# Оптимизация ASOF JOIN в ClickHouse

## Описание задачи

Задача описана [здесь](https://github.com/orientcap/clickhouse-asof-join)

## Структура репозитория

Репозиторий состоит из 2 папок: ``clickhouse-md-svr`` и ``python-client``.

В папке ``clickhouse-md-svr`` находится только файл ``compose.yml`` для запуска ClickHouse через ``docker compose``

В папке ``python-client`` размещен python-код для запуска тестов. Тесты также запускаются в контейнере, поэтому здесь находится второй файл ``compose.yml`` 

## Запуск теста

Предполагается запуск на хосте с Linux с установленным docker compose. Я использовал Alma 10, но должно работать на относительно свежих версиях других дистрибутивов.

Сначала необходимо перейти в папку ``clickhouse-md-svr`` и запустить ClickHouse:

``docker compose up -d``

Он скачает самый последний образ ClickHouse, создаст внутреннюю сеть, настроит имя сервера, порт, базу, пользователя.

Далее переходим в папку ``python-client``. Можно запустить непосредственно на хосте, имея установленный Python 3 (запускал на 3.12) с библиотекой ``clickhouse-connect``.

А можно поднять докер в интерактивном режиме:

``docker compose up``

Я запускал в докере. 

Будет сделано следующее:

1. Скачается образ python 3.12
2. Установится библиотека clickhouse-connect
3. Запустится тестирующий скрипт. Он использует сеть, базу и пользователя, созданные при старте контейнера с ClickHouse.
4. При желании можно настроить объем генерируемых данных в файле ``config.py``. Я не стал делать YAML из-за нехватки времени. По умолчанию ``NUM_QUOTES = 10000000``, ``NUM_TRADES = 100000``.
   Флаг ``REGENERATE_DATA`` должен быть равен ``True`` для первоначального создания датасета. В дальнейшем при экспериментах его можно выставить в ``False``, если нет задачи пересоздать схему с другими настройками таблиц.
5. Скрипт создает таблицы, заполняет их псевдо-реальными данными, пытаясь подобрать сделки в соответствии с квотами и распределяя их рандомно по временному диапазону, по биржам и тикерам. Разброс цен я попытался сделать реалистичным.
6. Дополнительно создается Materialized View с результатми ASOF JOIN для сравнения.
6. После создания датасета скрипт ждет, когда физическая структура файлов базы закончит перестройку с учетом партиционирования. Но, похоже, этот шаг не очень работает, поэтому я добавил дополнительное ожидание в 1 минуту после заполнения данных.
7. Далее запускается бенчмарки. Из-за отутствия времени я не успел оформить их как полноценный набор тестов, и в финале оставил только 3 варианта, которые показали различия в скорости. В процессе тестирования я менял очень много разных параметров, исправляя код DDL и код запроса и перезапуская тесты. Понимаю, что это надо было оформить как Test Cases, но просто не успеваю сейчас.
8. В конце печатается статистика по временам запуска.

Замечание. В папке sql лежат исходные DDL-скрипты из задачи, но я их не использую в коде, а использую свои, которые прописаны в строках в Python-коде. На красивое оформление, увы, не хватает сейчас времени.

## Анализ результатов

В процессе тестирования в первую очередь выяснилось, что на предложенном размере датасета (1М квот и 10k сделок) практически не видны никакие оптимизации - все работает одинаково быстро. Это связано с тем, что все данные помещаются в память с большим запасом, нет чтения с диска. А операции сортировки и поиска по партициям работают либо за O(1) либо за log(N).

При увеличении числа квот и сделок в 10 раз стали видны отличия для разных оптимизаций. Однако большинство оптимизаций касались схемы самих таблиц, а генерация такого датасета каждый раз занимает около 5 минут, поэтому набор из десятка тестов будет работать уже около часа, что затрудняет задачу для проверяющего.

Итак, что я смог измерить.

1. Сначала про вставку данных. Попробовал вставку батчами разного размера. Остановился на размере 100k. 1-10k примерно на порядок медленнее, что ожидаемо для колоночной СУБД. 50k для 1М записей - 3 секунды. 100k - 2 секунды. 1М - тоже 2 секкунды. Остановился на 100k, потому что накопление такого батча в реальной жизни - опасное дело из-за возможно потери данных при падении приложения. Но я не знаю важу специфику вставки. Возможно, у вас не так много источников данных, поэтому такие батчи накапливать нецелесообразно и лучше скидывать в базу почаще, не смотря на то, что это менее эффективно.
2. Далее пишем сам ASOF JOIN, добавил нессколько полей, чтобы проверить корректность данных:
```sql     
     SELECT 
         t.symbol,
         t.side as trade_side,
         t.qty as trade_qty,
         t.local_ts as trade_local_ts,
         q.local_ts as quote_local_ts,
         round(t.price, 5) as trade_price,
         round(q.bid_price, 5) as bid_price,
         round(q.ask_price, 5) as ask_price,
         round(t.price - q.bid_price, 5) as spread_to_bid,
         round(q.ask_price - t.price, 5) as spread_to_ask,
         dateDiff('microsecond', q.local_ts, t.local_ts) AS quote_to_request_latency_us
     FROM md_trades AS t
     ASOF LEFT JOIN md_quotes AS q
         ON t.symbol = q.symbol 
         AND t.local_ts >= q.local_ts
     PREWHERE t.local_ts between '2026-04-27 00:00:00' AND '2026-04-27 23:59:59.999'
```
Тестировал с фильром по времени и без него. Детали ниже. 

Для начала сравнил WHERE/PREWHERE. Ожидал, что PREWHERE должен быть быстрее, но по факту для нашего датасета примерно одинаковый результат.
